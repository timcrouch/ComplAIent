# ADR-0005: Authorization model with roles, scopes and server-side enforcement

Status: Accepted (2026-11-03)

## Context

The ISMS is used by organisations with several sites and departments. A CISO may be responsible for one site only, and an auditor for one department. Regulated customers expect every decision about access to be made and recorded on the server. The web app's UI hints alone are not enough, and neither is the user's chosen view mode. Some actions, such as role assignment and AI settings, are sensitive enough that a stolen but still-valid session should not be enough to perform them.

## Decision

- **Roles grant permissions.** `ROLE_PERMISSIONS` (`apps/api/src/authorization/roles.ts`) maps each `Role` to a fixed list of `Permission`s. Later plans extend these lists. Roles come only from application role assignments (ADR-0004), never from token claims.
- **Baseline permissions (P2-R14).** Every authenticated actor holds `me.read`, `me.update` and `organisation.read`, whatever their roles (`BASELINE_PERMISSIONS`). A newly provisioned user without a role can still load `/me` and see that they have no access. The organisation's name, its sites and departments, and its setup status are not secret from its own members, so every member may read them.
- **Scope matching.** Each role assignment has a scope:
  - **Organisation:** matches any resource, and the case where no resource is given.
  - **Site:** matches only a resource whose `siteId` equals the assignment's id.
  - **Department:** matches only a resource whose `departmentId` equals the assignment's id.
  - A site scope never matches a department id, and the reverse.
  - There is no hierarchy: a site role does not cover the departments of that site. A resource carrying both ids is matched by either a site assignment for its `siteId` **or** a department assignment for its `departmentId`.
  - **Services build `ResourceScope` from the persisted resource**, filling both `siteId` and `departmentId` from the stored record. They never take them from request input (path, query or body), so a caller cannot choose the scope that is checked.
  - `PolicyService.can(actor, permission, resource?)` grants access if any one assignment both carries the permission and matches the scope. With no resource, only organisation-scoped assignments count.
- **Default deny on bad data.** Assignments are typed, but they come from the database. An unknown role (including prototype keys such as `__proto__`), an unknown scope type, or a site or department scope whose id is null or empty grants nothing. An empty resource id never matches either. These cases never throw.
- **Scoped permissions (P2-R10).** Scoped evaluation is per permission, through the `SCOPED_PERMISSIONS` set (`AuthorizationModule.forRoot({ scopedPermissions })`). It is empty in Plan 2; Plan 3 adds the risk permissions. For a permission in the set:
  - the route guard accepts it held at any scope (`PolicyService.canAtAnyScope`), so a site-scoped risk owner can reach the route;
  - the service then checks the stored resource with `PolicyService.assertCanAccess(actor, permission, resource)`, and filters lists with `PolicyService.accessScope(actor, permission)`, which is `organisation`, `units` (the site and department ids) or `none`;
  - `permissionsFor` reports it.
  - A permission outside the set keeps the organisation-level route check (R19).
  - **`controls.test` is not scoped (ruling, #24, 2026-11-07).** A control test sets the organisation-wide Statement of Applicability status and the library's latest result, so only an organisation-scoped `ciso` or `risk_owner` may record one or ask for AI test steps. A site- or department-scoped holder may still read the library and a control's operation, with `canRecordTest: false`. This restores Plan 6's intent, which commit 748c4bb had widened without a resource check.
- **Out-of-scope resources are 404 by design.** `assertCanAccess` refuses with `404 NOT_FOUND` "Not found", not `403`. A caller must not learn that a resource outside their units exists, so a missing resource and a hidden one look the same.
- **`permissionsFor(actor)`** returns exactly what the route guard grants (Ruling R21): the baseline, the permissions of organisation-scoped assignments, and each scoped permission held at any scope, without duplicates. For every `p` the guard's rule (`canAtAnyScope` for a scoped `p`, `can` otherwise) holds exactly when `p` is returned, and a property test checks this over every combination of a set of assignments. Unscoped permissions held only through site or department assignments are not listed. Those assignments stay visible in `MeResponse.roles`, so the web app can show them, but a permission list never claims a route-level access the guard would refuse. `/me` returns this list so the web app can hide actions.
- **Server-side enforcement.** One global guard, `AccessGuard`, runs `AuthGuard` and then `PermissionGuard`. Both run inside a single composite guard, so the order is fixed by the code and does not depend on the order in which modules register `APP_GUARD`. `PermissionGuard` handles routes as follows:
  - **Public routes** (health, ready, openapi.json) pass. Any other request without an actor fails closed with `UNAUTHENTICATED`.
  - **`route.permission`** is checked at organisation level (`can(actor, permission)` with no resource), except a scoped permission (P2-R10), which passes when held at any scope (`canAtAnyScope`). If it fails, the guard returns `403 FORBIDDEN` "You don't have access to this". Routes that act on a scoped resource must also call `PolicyService.can` with that resource's scope in the service. The route-level check alone does not grant access to a site-scoped actor.
  - **A contract route without a permission** needs authentication only.
  - **A route without contract metadata** is still authenticated by `AuthGuard` (default deny, ADR-0004).
- **View mode never grants access.** `viewMode` (guided, professional, executive) changes only presentation. No policy decision reads it, and the web app hides only what the API reports as unavailable. The user's choice is stored on `User.viewMode`; NULL means "not chosen", and `/me` then returns the default for the user's roles. Saving it (`PATCH /me/preferences`, permission `me.update`, held by every authenticated user) is not audited: it is presentation only and grants nothing. Add auditing later if an auditor asks for it.
- **Recent authentication.** On a route with `recentAuth: true`, `PermissionGuard` checks when the actor last signed in interactively:
  - **Only a real `auth_time` claim counts** (Ruling R22). For identity, `JwtVerifier` falls back to `iat` when `auth_time` is absent, and records which one it used (`authTimeSource: "auth_time" | "iat"` on `VerifiedToken` and `Actor`). `iat` is renewed on every token refresh, so it says nothing about a recent sign-in. A token whose time came from `iat` always gets `RECENT_AUTH_REQUIRED` on these routes, however fresh it is.
  - If `now - authTime > 300` seconds, it returns `403 RECENT_AUTH_REQUIRED` "Please sign in again to continue". Exactly 300 s still passes.
  - The clock is the injectable `Clock` from `@isms/domain`. One `CLOCK` provider (from `IdentityModule`) serves both the verifier (expiry, future `auth_time`) and this check, so they cannot disagree about the time.
  - The permission is checked first, so a user without access gets `FORBIDDEN` and is not asked to sign in again.
  - `JwtVerifier` rejects an `auth_time` in the future, which would otherwise defeat this check (ADR-0004).
- **Role assignment is sensitive (P2-R5).** `GET /users` needs `users.list`. Granting (`POST /users/{userId}/roles`) and revoking (`DELETE /role-assignments/{assignmentId}`) need `roles.assign` at organisation scope and a recent sign-in (`recentAuth`); the web steps up with `max_age=0`. Each grant and revoke writes its audit row (`identity.role_granted`, `identity.role_revoked`) in the same transaction as the change.
- **Last administrator (implemented).** `RoleAssignmentService.revoke` refuses with `409 CONFLICT`, detail path `lastAdministrator` (P2-R8), to remove the only organisation-scoped `administrator` assignment, including the caller's own. Site- or department-scoped administrators do not count. The count and the delete run in one transaction holding the advisory lock the bootstrap grant uses (`BOOTSTRAP_ADMIN_LOCK`, `isms:bootstrap-admin`), so two administrators revoking each other at once are serialised and exactly one remains. Otherwise `BOOTSTRAP_ADMIN_EMAIL` would arm itself again (ADR-0004). Assignments are never edited in place (a scope change is a revoke plus a grant), and there is no user deactivation yet; any later change of that kind must apply the same rule under the same lock.
- **Separation of duties on risk approval (P3-R4, Plan 3).** The rules are pure functions in `@isms/domain` (`approvalRule`, `approvalRefusal`); the API (`ApprovalService`, `apps/api/src/risks/approval-readiness.ts`) is authoritative and the web only reflects `RiskDetailDto.can` and `approval.viewerRefusal`.
  - The **reviewer** is the person who submitted the risk (`POST /risks/{id}/submit`, `risks.review` at the risk's scope).
  - The **reporter** never approves a risk they reported (`approvalRefused.reporter`), even holding `risks.approve`.
  - The reviewer may approve only when the score is at or below the appetite threshold and the treatment is not `accept` (`reviewerMayApprove`); otherwise `approvalRefused.reviewerNeedsIndependent`. Under `reviewerMayApprove` the reviewer needs no `risks.approve`: holding `risks.review` (or `risks.approve`) at the risk's scope is enough (spec §8.3), and a reviewer who holds neither any more is `approvalRefused.notApprover`.
  - Anyone else needs `risks.approve` at a scope matching the risk (`approvalRefused.notApprover` otherwise). The approve and return routes require only `risks.read`, so these refusals come from the service, as `409 CONFLICT` details, after the visibility (404), state (`invalidTransition`) and version (`staleVersion`) checks.
  - Returning is open to the reviewer (to withdraw the risk) and to anyone who could approve it; the comment is required.
  - **There is no override.** When no one can approve, the detail reports `approval.noEligibleApprover` and the risk waits. `eligibleApproverCount` counts the users for whom `approvalRefusal` is null: holders of `risks.approve` at a matching scope, less the reporter and the reviewer, plus one for the reviewer when the rule is `reviewerMayApprove` and the reviewer is not the reporter (and still holds `risks.review` or `risks.approve` there). `awaitingMyApproval` applies the same rule: risks someone else reviewed in the actor's `risks.approve` units, and risks the actor reviewed that are within appetite and not accepted, in their `risks.review` or `risks.approve` units.
  - Each decision locks the risk row (`SELECT … FOR UPDATE`) and writes an append-only `Approval` naming the decided version, with that version's snapshot plus the evidence ids and SHA-256 hashes; the unique key (risk, version, decision) makes a double approval impossible, and a violation becomes `409 staleVersion`.
  - **Self-grant.** Role grants have no separation-of-duties rule of their own. SoD is evaluated at approval time against the actor's current role assignments, read from the database inside the decision's transaction, after the risk row lock, with `FOR SHARE` on those assignments. A user who grants themselves the approver role still cannot approve a risk they reported, or one they reviewed when the rule needs an independent approver; and a revoked role stops counting at once.

## Consequences

- Adding a permission means extending the `Permission` contract, `ROLE_PERMISSIONS` and the policy tests. Routes declare permissions in their contract, so OpenAPI documents them (`x-permission`, `x-recent-auth`).
- A site-scoped actor can reach only routes whose service performs a resource-scoped check. Route-level permissions are deliberately organisation-level.
- The web app handles `RECENT_AUTH_REQUIRED` as implemented: the BFF maps it to a step-up sign-in with `max_age=0` (`apps/web/lib/server-api.ts`, `stepUpPath` in `apps/web/lib/viewer.ts`), the user signs in again and is returned to the page, and then retries the action.
- Changing the 300 s window means changing `RECENT_AUTH_WINDOW_S` and this ADR.
