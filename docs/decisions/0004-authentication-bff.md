# ADR-0004: Authentication through a backend-for-frontend; the API is a pure resource server

Status: Accepted (2026-11-03)

## Context

The ISMS signs users in through an external OpenID Connect identity provider (Keycloak locally, the customer's IdP in production). Browser-held tokens are exposed to XSS and token theft. Regulated customers expect sessions that can be revoked centrally, role changes that are audited inside the application, and an API that can be reached only with a valid, short-lived token.

## Decision

- **BFF.** The web app (Next.js) is the only OIDC client (`isms-web`, confidential, authorization code + PKCE S256, no direct grants). It keeps access and refresh tokens server-side in its session and never sends them to the browser. The browser holds only an opaque, HttpOnly session cookie. The web app calls the API with `Authorization: Bearer <access token>`.
- **The API is a pure resource server.** It holds no OIDC client credentials and no sessions. For each request it verifies the bearer token (`JwtVerifier`, `jose`):
  - signing keys come from the issuer's discovered `jwks_uri`, with an explicit fetch timeout; the discovery document's `issuer` must equal the configured issuer;
  - only `RS256` and `ES256`; exact `iss` and `aud` (`OIDC_AUDIENCE`, added by an audience mapper); `exp` and `sub` required; 30 s clock tolerance;
  - required claims: `sub`, `email`, boolean `email_verified`, `name` (or `preferred_username`), and `auth_time` (falling back to `iat`), used later for recent-authentication checks;
  - only access tokens: a token whose protected header has `typ` `ID` (case-insensitive; Keycloak ID tokens) is rejected, and so is any token that carries a `nonce` claim (access tokens never do; code-flow ID tokens always do, because the BFF sends a nonce). This matters for customer IdPs that can put the API audience on ID tokens. If `OIDC_ACCESS_TOKEN_TYP` is set (for example `at+jwt`, RFC 9068), the header `typ` must equal it, compared case-insensitively. It is unset by default, because Keycloak access tokens carry `typ` `Bearer` and Entra ID and Okta tokens carry `JWT`;
  - an unknown `kid` triggers at most one JWKS refetch per 30 s cooldown (key rotation without a JWKS-refetch amplification attack);
  - failure to obtain keys returns `503 AUTH_UNAVAILABLE`; every other failure returns `401 UNAUTHENTICATED` with the fixed message "Sign-in required". The verifier's reason is logged as an error code only, never returned, and tokens are never logged.
- **Default deny.** A global `AuthGuard` requires a token on every route, including routes without contract metadata. The only exceptions are `/api/v1/health`, `/api/v1/ready` and `/api/v1/openapi.json` (exact path, no permission on the route). The header must be exactly `Bearer <token>`.
- **Users are provisioned just in time** on `(issuer, subject)`; `email`, `displayName` and `lastSeenAt` are refreshed from the token: a changed email or display name is written at once, and `lastSeenAt` is written at most every 5 minutes (`LAST_SEEN_WRITE_INTERVAL_MS`). Email is a profile attribute, not an identity key.
- **Roles are assigned in the application**, not taken from IdP groups or token claims. A role change is a domain action with an audit trail. The only automatic grant is the **bootstrap administrator**. It is not strictly one-time: it applies at any sign-in while no `administrator` assignment exists, `BOOTSTRAP_ADMIN_EMAIL` is set, and the token's email is verified and matches it case-insensitively, that user receives organisation-scoped `administrator`. A user who already holds organisation-scoped `administrator` skips the check. The check and insert run under a transaction-scoped PostgreSQL advisory lock, so concurrent first sign-ins cannot create two administrators. The grant is audited as `identity.bootstrap_admin` (from Task 8).
- **IdP group to role mapping is deferred to Plan 4.**

### Web BFF sessions (Task 11)

- **Session store.** Sessions live in Redis, which is a shared service. The stored value `{ accessToken, refreshToken, idToken, expiresAt, refreshExpiresAt, userSub, createdAt }` is therefore **encrypted at rest** with AES-256-GCM, using a random 96-bit IV. The key is derived from `SESSION_SECRET` with HKDF-SHA256. The Redis key is the GCM additional authenticated data, so a value copied to another key does not decrypt. The Redis key is `sess:<HMAC-SHA256(id)>`, using a second HKDF-derived key. Anyone who can read Redis sees neither the tokens nor the session ids that would let them replay a cookie. The Redis TTL equals the refresh-token lifetime (`refresh_expires_in`, falling back to 30 min). Rotating `SESSION_SECRET` invalidates every session.
- **Cookie.** The cookie holds only the session id: 32 random bytes, base64url. Its attributes are `HttpOnly; SameSite=Lax; Path=/`, with no `Max-Age`, so Redis is the authority on lifetime. It is `Secure` and named `__Host-isms_session` unless `WEB_BASE_URL` is plain `http://localhost` or `http://127.0.0.1` (any port; `isLocalHttp`, `apps/web/lib/web-url.ts`), where it is `isms_session` without `Secure`. Any other `http://` host still gets `Secure`, so such a deployment fails closed.
- **Login.** `/auth/login` uses authorization code + PKCE S256 with `state` and `nonce`. `{ state, codeVerifier, nonce, returnTo }` is stored encrypted under `oidc:<state>` for 10 min and read with `GETDEL`, so each state is single-use. A short-lived `isms_login` cookie carries the `state` and must match at the callback. This prevents login CSRF, where an attacker's callback URL would sign the victim in as the attacker. `returnTo` passes `safeReturnTo` and is never sent to the IdP. `safeReturnTo` accepts only same-origin paths. It rejects `//`, backslashes, control characters, `/auth/*`, and anything that turns unsafe after any of up to three rounds of percent-decoding.
- **Callback failure.** Any callback failure redirects once to `/auth/login?error=signin`. That page never redirects by itself, so a broken IdP cannot cause a loop. Only fixed reason codes are logged, never codes, tokens or IdP messages. All redirects are built from `WEB_BASE_URL`, never from the `Host` header.
- **Token rejected by the API.** If the API answers 401 for a session younger than 60 s (`createdAt`), the IdP is issuing tokens the API refuses (no email, no `email_verified`, wrong audience, clock skew). Its SSO session would sign the user straight back in, so the BFF destroys the session and shows a terminal "This account can't be used here" screen instead of redirecting. A 401 for an older session redirects once to sign-in as before.
- **Refresh.** `getAccessToken` refreshes when fewer than 30 s remain. Keycloak rotates refresh tokens, so concurrent requests share one refresh. They coordinate through a Redis lock (`SET NX PX 20000`, with a compare-and-delete release) and re-read the session after acquiring the lock. The write-back uses `SET XX`, so a logout during a refresh is never undone. A failed refresh destroys the session. So does a change of subject, which is checked when the refresh response carries an ID token with a `sub` claim (`apps/web/lib/session.ts`, `refresh` in `apps/web/lib/oidc.ts`). Keycloak always returns one. With an IdP that returns no ID token on refresh, the stored subject is kept and the check does not run; the API still verifies every access token itself.
- **Logout (CSRF).** `/auth/logout` is **POST only**: there is no GET handler, so Next.js answers 405. The request must be same-origin. If `Sec-Fetch-Site` is present it must be `same-origin`, and if `Origin` is present it must equal the `WEB_BASE_URL` origin. A request with neither header is refused. On success the handler destroys the session, clears the cookie and sends a 303 to the IdP end-session endpoint with `id_token_hint`, `client_id` and `post_logout_redirect_uri = WEB_BASE_URL + "/"`.
- **Proxy.** Next.js 16 renamed `middleware.ts` to `proxy.ts`, which runs on Node. The proxy only checks that the cookie is present, and with the cookie present replaces `x-request-id` with a fresh UUID (#5). Route handlers on the paths it skips (the auth routes, the evidence uploads, the report files) mint their own id with `withRequestId(crypto.randomUUID(), …)` (`apps/web/lib/request-id.ts`), so a client-chosen request id is never forwarded to the API. It redirects app routes without a cookie to `/auth/login?returnTo=…`, and excludes `/auth/*`, `/_next/*` and static files. The server-side `(app)` layout validates the session for real (Task 12).

## Consequences

- Tokens never reach browser JavaScript; XSS cannot exfiltrate them. The web app must implement refresh and logout (Task 11).
- The API can run behind any standards-compliant OIDC provider that issues JWT access tokens with the required claims and an audience for the API. For Keycloak 26 that means the client must carry the `basic` client scope (it emits `sub` and `auth_time`).
- Revocation takes effect within the access-token lifetime (300 s locally); the API does not introspect tokens.
- Each request reads the user row; it writes only when the profile changed or `lastSeenAt` is at least 5 minutes old. `lastSeenAt` is therefore accurate to within 5 minutes.
- `BOOTSTRAP_ADMIN_EMAIL` has no effect while any administrator exists, but it applies again if the administrator count ever drops to zero. Removal of the last organisation-scoped administrator is therefore refused (`RoleAssignmentService.revoke`, `apps/api/src/identity/role-assignment.service.ts:153-170`, under the same advisory lock; ADR-0005). Operators should also unset `BOOTSTRAP_ADMIN_EMAIL` after setup.
