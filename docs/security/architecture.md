# Security architecture

Status: last reviewed against the code on 2026-11-08 (issue #6): the Plan 1 foundation plus the risk slice, the AI gateway and evidence storage (sections 9 to 13), and the optional EU AI Act module (section 14). Keep this document in step with the code: a change to a trust boundary, a token or session flow, a secret, or a logging rule updates it in the same pull request.

The security baseline is **OWASP ASVS Level 2** (foundation design §3). This document describes the foundation that later plans build on: the trust boundaries, how tokens and sessions flow, the authorisation layers, the audit trail, the secrets, the logging rules, and a threat list mapped to ASVS chapters. The decisions behind it are in ADR-0004 (authentication), ADR-0005 (authorisation), ADR-0006 (audit history) and ADR-0007 (deployment).

## 1. Components and trust boundaries

```
 Browser ──HTTPS──▶ Web BFF (isms-web) ──Bearer JWT──▶ API (isms-api) ──▶ PostgreSQL
    │                    │      │                         │      │
    │                    │      └──▶ Redis (sessions) ◀───┘      └──▶ Object storage (Plan 2+)
    └──redirect──▶ IdP (OIDC) ◀── code exchange, JWKS ────┘
                                         Worker (isms-worker) ──▶ Redis (BullMQ)
                                         AI provider (Plan 3) ◀── API's AI gateway only
```

Each line crossing between two boxes is a trust boundary. Everything the API receives is untrusted until it is verified at that boundary.

| Component                                                   | Trust level                                        | What it holds                                                         | Boundary controls                                                                                                                                                                              |
| ----------------------------------------------------------- | -------------------------------------------------- | --------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Browser**                                                 | Untrusted                                          | An opaque, HttpOnly session cookie, and nothing else                  | No tokens ever reach browser JavaScript. Same-origin checks on state-changing BFF routes.                                                                                                      |
| **Web BFF** (`isms-web`, Next.js)                           | Trusted server, internet-facing                    | The OIDC client secret, `SESSION_SECRET`, encrypted sessions in Redis | It is the only OIDC client. It only hides actions the API reports as unavailable and makes no access decisions.                                                                                |
| **API** (`isms-api`, NestJS)                                | Trusted, the policy decision and enforcement point | The database application role                                         | It verifies every bearer token itself, and every business rule and permission check lives here. Default deny.                                                                                  |
| **Worker** (`isms-worker`)                                  | Trusted, internal only                             | The Redis connection                                                  | It has no inbound HTTP except liveness (`:9465/healthz`) and metrics (`:9466`). Job payloads are validated with Zod.                                                                           |
| **PostgreSQL**                                              | Trusted store                                      | All domain data and the audit trail                                   | Separate roles for the owner (migrations) and the application (runtime). The application role cannot change or delete audit rows.                                                              |
| **Redis**                                                   | Shared and semi-trusted                            | BFF sessions (encrypted), login state (encrypted), BullMQ queues      | Session values are encrypted with AES-256-GCM and keys are HMACed, so reading Redis yields no tokens and no replayable ids (ADR-0004).                                                         |
| **Object storage** (S3-compatible)                          | Trusted store, used from Plan 2                    | Evidence files                                                        | Reached only by the API (section 11). Development uses MinIO (`bitnamilegacy/minio`, **dev only**, Ruling R8). Plan 4 chooses a maintained S3-compatible store for production and on-premises. |
| **IdP** (Keycloak locally, or the customer's OIDC provider) | External, trusted for identity only                | Users and credentials                                                 | Discovery `issuer` must match. JWKS is fetched with a timeout and a refetch cooldown. Roles are never taken from IdP claims.                                                                   |
| **AI provider** (OpenRouter, Plan 3)                        | External, untrusted output                         | Nothing persistent (zero data retention, EU endpoints)                | Only the AI gateway (`@isms/ai`, used by the API and the worker) calls it, and it refuses calls until the privacy settings are on (section 9).                                                 |

The container images run as the non-root uid 10001. Their code is owned by root, so the service cannot modify what it runs, and they contain no secrets (ADR-0007). Host ports in the local compose stack bind to `127.0.0.1` only.

## 2. Tokens and sessions

### Sign-in (authorization code + PKCE)

1. The browser requests an app route without a session cookie. The `proxy.ts` presence check redirects it to `/auth/login?returnTo=…`, where `returnTo` passes `safeReturnTo` and only same-origin paths are accepted.
2. `/auth/login` creates `state`, `nonce` and a PKCE S256 verifier. It stores them encrypted under `oidc:<state>` for 10 minutes, sets a short-lived `isms_login` cookie carrying `state`, and redirects (303) to the IdP.
3. The user authenticates at the IdP. The application never sees a password.
4. `/auth/callback` reads `oidc:<state>` with `GETDEL`, so each state works once, and checks it against the `isms_login` cookie to prevent login CSRF. It exchanges the code with the client secret and validates the ID token and nonce. It then creates a session: a random 32-byte id in the cookie, and `{ accessToken, refreshToken, idToken, expiry, sub }` encrypted in Redis under `sess:<HMAC(id)>`.
5. Any callback failure redirects once to `/auth/login?error=signin`, which never redirects on its own. Only fixed reason codes are logged.

### Calling the API

- Server components and route handlers call the API with `Authorization: Bearer <access token>`, which is read from the session server-side.
- `getAccessToken` refreshes when fewer than 30 s remain. Concurrent requests share one refresh under a Redis lock. A failed refresh destroys the session. So does a change of subject, which is checked when the refresh response carries an ID token with a `sub` claim (`apps/web/lib/oidc.ts:137-146`, `apps/web/lib/session.ts:121-123`); Keycloak always sends one. With an IdP that returns no ID token on refresh, the stored subject is kept and the check does not run.
- The API verifies the JWT on every request (`JwtVerifier`, `jose` pinned at 6.2.14, Ruling R16):
  - only RS256 and ES256;
  - exact `iss` and `aud`;
  - `exp`, `sub`, `email`, `email_verified` and `name` required (`name` falls back to `preferred_username`);
  - 30 s clock tolerance;
  - an `auth_time` in the future is rejected;
  - only access tokens are accepted (#4): a protected-header `typ` of `ID` (case-insensitive; Keycloak ID tokens) fails, and so does any token with a `nonce` claim (code-flow ID tokens always carry one, because the BFF sends a nonce). This matters for an IdP that can put the API audience on ID tokens. With `OIDC_ACCESS_TOKEN_TYP` set (for example `at+jwt`, RFC 9068), the header `typ` must equal it, compared case-insensitively. It is unset by default, so Keycloak's `Bearer` and the `JWT` of Entra ID and Okta pass;
  - an unknown `kid` causes at most one JWKS refetch per 30 s.
- If keys cannot be obtained the API answers `503 AUTH_UNAVAILABLE`. Every other failure answers `401 UNAUTHENTICATED` with a fixed message.

### Session lifetime and sign-out

- The cookie is `HttpOnly; SameSite=Lax; Path=/`, and `Secure` with the `__Host-` prefix on every origin except plain `http://localhost` and `http://127.0.0.1` (any port; `isLocalHttp`, `apps/web/lib/web-url.ts:5-7`). `WEB_BASE_URL` must be `https`, or plain `http` on those two hosts only. It has no `Max-Age`: the Redis TTL (the refresh-token lifetime) is the authority.
- Every `(app)` page validates the session server-side. An expired session leads to exactly one redirect to sign-in (Task 12).
- `/auth/logout` is POST only and same-origin only (`Sec-Fetch-Site` / `Origin`). It deletes the session, clears the cookie and redirects to the IdP end-session endpoint with `id_token_hint`.
- Revocation at the IdP takes effect within the access-token lifetime (300 s locally). The API does not introspect tokens.
- Rotating `SESSION_SECRET` invalidates every session.

### Recent authentication

Sensitive routes (`recentAuth: true`, such as role assignment or AI settings in later plans) require an interactive sign-in within the last 300 s. **Only a real `auth_time` claim counts (Ruling R22).** When the verifier fell back to `iat`, it records the source, and such a token always gets `403 RECENT_AUTH_REQUIRED`, because `iat` is renewed on every refresh.

## 3. Authorisation layers

1. **Authentication, default deny.** A global `AccessGuard` runs `AuthGuard` first. Every route needs a valid token except `/api/v1/health`, `/api/v1/ready` and `/api/v1/openapi.json`, which are matched on the exact path.
2. **Module gate, then route permission (Rulings R19, R20; ADR-0005 P2-R10).** `AccessGuard` runs, in this fixed order, `AuthGuard`, the module gate and `PermissionGuard` (`apps/api/src/authorization/require-permission.ts:71-84`).
   - **Module gate.** A route of an optional module (`RouteDef.module`) answers `404 NOT_FOUND` while the module is off, whoever asks (`module-gate.ts:20-25`). It runs before the permission check, so a caller without the permission learns nothing more than one with it. It reads `OrganisationModule` on every request, so a switch takes effect at once (section 14).
   - **Route permission.** For most permissions the guard calls `can(actor, permission)` with no resource, which only an organisation-scoped assignment satisfies. The exceptions are the seven `DEFAULT_SCOPED_PERMISSIONS` (`apps/api/src/authorization/scoped-permissions.ts:19-27`): `risks.report`, `risks.read`, `risks.review`, `risks.approve`, `ai.transcripts.read`, `library.read` and `reports.read`. Each of these passes the guard when held at any scope, including a site or department (`canAtAnyScope`, `require-permission.ts:54-58`); the service must then check the stored resource (item 3). `controls.test` is deliberately not in the list (#24).
   - **Baseline.** Every authenticated actor holds three baseline permissions, whatever their roles: `me.read`, `me.update` and `organisation.read` (`BASELINE_PERMISSIONS`, `roles.ts:77-81`; Ruling R18, P2-R14).
   - **EU AI Act permissions.** `aiact.read` and `aiact.manage` are organisation-scoped only: they are not in the scoped list, so a site- or department-scoped assignment does not grant them (`roles.ts:3-8`).
3. **Resource scope in services (Ruling R19).** A service acting on a site- or department-scoped resource calls `PolicyService.can(actor, permission, scopeOf(persistedResource))`. The scope comes from the stored record and never from request input. A site-scoped actor reaches only routes whose service performs this check. Recording a control test (`controls.test`) is organisation-level only, because a test changes the organisation-wide SoA status (ADR-0005, #24).
4. **Recent authentication** for `recentAuth` routes (section 2). The permission is checked first.
5. **What the UI is told (Ruling R21).** `permissionsFor(actor)` returns exactly what the route guard grants (`policy.service.ts:133-142`): the three baseline permissions, every permission of an organisation-scoped assignment, and each of the seven scoped permissions held at any scope. An unscoped permission held only through a site or department assignment is not listed. A property test checks that the list and the guard agree. The web app hides only actions the API reports as unavailable. It never grants anything, and view mode never affects a decision.

Roles come only from application role assignments, never from token claims. Unknown roles, unknown scope types, and empty or null scope ids grant nothing. The only automatic grant is the audited bootstrap administrator (ADR-0004). Removing the last organisation-scoped administrator is refused with `409 CONFLICT` (`lastAdministrator`), under the bootstrap advisory lock (`apps/api/src/identity/role-assignment.service.ts:153-170`, ADR-0005).

## 4. Audit immutability

- `AuditEvent` is the audit trail, with one writer, `AuditService.record` (ADR-0006). It is one of eleven append-only tables. The schema marks each with a `/// Append-only` or `/// Insert-only` doc comment (`packages/database/prisma/schema/*.prisma`): `AuditEvent`, `RiskScale`, `RiskScaleLevel`, `RiskVersion`, `Approval`, `ConcernMessage`, `Evidence`, `EvidenceControl`, `ControlTest`, `ControlTestEvidence` and `BoardNarrative`. For each, the migrations revoke `UPDATE`, `DELETE` and `TRUNCATE` from `isms_app`. `packages/database/test/append-only-grants.int.test.ts` reads the annotations from the schema and checks those privileges for every marked table, so a newly marked table is covered without editing the test.
- `AiInteraction` is not marked append-only: `isms_app` has `INSERT` and `SELECT`, and `UPDATE` on the two columns `outcome` and `discardedCount` only; `DELETE` and `TRUNCATE` are revoked (migration `20261105000100_ai_gateway`, `packages/database/test/ai-grants.int.test.ts`; section 9).
- On `AuditEvent` the runtime role `isms_app` has `INSERT` and `SELECT` only, and a row trigger rejects `UPDATE` and `DELETE` even for the owner. The other append-only tables rely on the revoked privileges, without a trigger.
- Deliberately mutable, with their history in the audit trail: the EU AI Act module's `OrganisationModule`, `AiSystem`, `AiSystemObligation` and `AiSystemRisk` (section 14), like the other working tables (`Risk`, `RoleAssignment`, …).
- `TRUNCATE` remains possible for the owner role, which is used only by migrations, the test reset of `isms_test` (Ruling R3), and demo mode. With `DEMO_TOOLS_ENABLED=true` (Phase 3 design §5.1, §5.4) the API's demo module, and the `pnpm demo:load` and `pnpm demo:reset` commands, truncate the instance's database as the owner role to reset it or load sample data. This erases the audit trail by design; the trail then starts again with `demo.reset`. A statement-level trigger is a later hardening step. The guards:
  - the setting, plus the demo instance being its own deployment. Without `DEMO_TOOLS_ENABLED=true` the API never reads `DATABASE_OWNER_URL` and the demo routes do not exist, and the CLI refuses to start (`packages/demo/src/cli/shared.ts:22-24`);
  - in the API: `organisation.manage`, a recent sign-in (`recentAuth`) and a typed confirmation that must equal the organisation name (or `RESET` when there is none), trimmed and compared case-sensitively (`400 confirmationMismatch`);
  - in the CLI (#7, `packages/demo/src/cli/guard.ts:29-52`): an unknown option is refused, so a typo cannot skip the question; `NODE_ENV=production` is refused unless `--allow-production` is given; then a `y/N` question names the database. `--yes` (`-y`) skips the question; without a terminal the command refuses unless `--yes` is given;
  - a sign-in fence (#7): the load and the reset take the advisory lock `isms:demo` exclusively before they truncate (`packages/demo/src/reset.ts:27`). In demo mode every sign-in takes the same lock shared, around its placeholder claim and user upsert (`apps/api/src/identity/user-provisioning.service.ts:111-119`). A sign-in therefore waits for a running load, and a load for running sign-ins, so a load cannot leave a duplicate user without roles;
  - a capped lock wait (#7, `packages/database/src/truncate.ts:56-91`): the truncate locks every table in one `LOCK TABLE` statement, sorted by name, with each attempt bounded by a `statement_timeout` of 200 ms, below Postgres's `deadlock_timeout`. On a timeout it rolls back to a savepoint, which releases the locks, waits and tries again, up to 50 attempts, then fails with a plain message. The deadlock detector never runs, so an application transaction is never the one cancelled.
- An audited change passes its transaction client, so the change and its audit row commit or roll back together.
- Snapshots are normalised to JSON, and every credential-like key is **removed** at any depth. The rule is the same as the log scrubber's.
- `requestId` and `traceId` are correlation aids, not evidence. The actor and the timestamp are the authoritative fields.

Controls:

- `.gitignore` excludes `.env*` (except `.env.example`), `*.key` and `*.pem`. `.dockerignore` excludes the same files from every image build context.
- `.env.example` holds only values starting with `dev-placeholder-`.
- **gitleaks** scans the full git history in CI, with the default rule set. Its allow-list (`.gitleaks.toml`) has five entries, each with `condition = "AND"`: an entry needs both a path match and a value match, so any other secret in the same file is still reported. The entries are the `dev-placeholder-*` values in `.env.example`; the realm's `${OIDC_CLIENT_SECRET}` substitution in `infrastructure/docker/keycloak/realm-isms.json`; values in test code (`apps/*/test/`, `packages/*/test/`, `e2e/`) that name themselves fake, dummy, placeholder or not-a-real; the CI test-only `AI_SECRETS_KEY` in `.github/workflows/ci.yml` (and its decoded digits); and one made-up OpenRouter key in `apps/web/test/settings/`.
- Configuration errors name the variable and the problem, never the value (`@isms/config`).

## 6. Logging and redaction

- Logs are structured JSON (pino), with `service`, `requestId` and the trace id when one is active. The BFF gives each server request its own UUID, sends it to the API as `x-request-id` on every call, and adds it to its log events, so a BFF event and the API request it caused share one id (#5). A client-chosen value is never forwarded or logged. On the paths its matcher covers, the proxy replaces `x-request-id` with a fresh UUID (`apps/web/proxy.ts:28-33`). The paths it skips (the auth routes, paths ending in a file extension such as the report files, and the evidence uploads) would pass the client's header through, so their route handlers run under `withRequestId(crypto.randomUUID(), …)` (`apps/web/lib/request-id.ts:19-21`): `/auth/login`, `/auth/callback`, `/auth/logout`, `lib/upload.ts` and `/reports/files/[file]`. The API accepts an inbound `x-request-id` matching `^[A-Za-z0-9-]{8,64}$` and generates one otherwise (`apps/api/src/platform/request-id.ts`); it remains a correlation aid only (section 4).
- **Key-based scrubbing at every depth (`@isms/telemetry` `scrub`).** Values under keys that match `token`, `secret`, `passw(o)rd`, `authorization`, `cookie`, `api[-_]key`, or a key ending in `key`, are replaced with `[Redacted]`. This applies inside arrays and error `cause` chains, up to a depth of 10 (deeper subtrees are redacted whole). The request, response and error serializers are scrubbed too. Exact `redact` paths for `authorization`, `cookie` and `set-cookie` headers sit behind it as a second layer.
- **Secrets embedded in strings are not redacted (Ruling R15).** The scrubber works on keys. A token pasted into a free-text field, a URL with a password in it, or an error message quoting a header would pass through. Code therefore never logs raw configuration, connection URLs, request bodies, IdP error messages, authorization codes or tokens. The BFF logs event names and fixed reason codes only, and the API logs verifier failures as error codes only.
- Errors returned to clients use the fixed contract `{ error: { code, message, requestId, details? } }`. Messages are fixed per code, and internal errors carry no stack or cause.
- Audit snapshots apply the same key rule but **remove** the keys (section 4).

## 9. AI gateway (Plan 3)

- **One path to the provider.** Business code calls typed purposes through the gateway in `@isms/ai`, used by the API and by the worker (control suggestions run as a job). The purposes are the eight of `AiPurpose` (`packages/ai/src/store.ts:4-12`): `concern_turn`, `control_suggestion`, `framework_suggestion`, `posture_summary`, `control_test_steps`, `ai_act_classification`, `ai_act_obligation_guidance`, and the administrator's `connection_test`. Nothing else holds a provider client. `AI_PROVIDER=mock` exists for tests and e2e and is refused in production.
- **Privacy routing.** With EU-only routing on, calls go to OpenRouter's EU endpoint (`https://eu.openrouter.ai/api/v1`). Every request carries provider routing `zdr: true`, `data_collection: "deny"` and `require_parameters: true`, and the model list on the settings screen is filtered to zero-data-retention endpoints. The gateway refuses every business call (every purpose except `connection_test`) while the master switch, either privacy switch, the key, `AI_SECRETS_KEY` or the purpose's model is missing (`aiUnavailable.<reason>`). One development-only exception: `AI_ALLOW_NON_EU_ROUTING=true` lets AI run with EU-only routing off (zero retention stays required), and it is refused when `NODE_ENV=production` (`packages/config/src/schemas.ts`). The administrator's `connection_test` ignores the master switch and the purpose models (it tests the key before AI is switched on), but still needs both privacy switches, the key and `AI_SECRETS_KEY`.
- **What each purpose sends.** Only these fields leave the installation (the prompt builders are in `packages/ai/src/purposes/`; the gateway's own `connection_test` sends the fixed prompt `Reply with {"ok":true}.`):

  | Purpose                                               | Runs in, model    | Data sent                                                                                                                                                                                                                      |
  | ----------------------------------------------------- | ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
  | `concern_turn`                                        | API, conversation | The organisation's site names and the asset types (system prompt); the reporter's own messages in the conversation (user messages).                                                                                            |
  | `control_suggestion`                                  | Worker, controls  | The risk's title, scenario, threat, consequence and existing safeguards; up to 15 candidate library controls (code, title, requirement references).                                                                            |
  | `framework_suggestion`                                | API, frameworks   | The organisation's name, description and approximate headcount, the country codes of its sites, and the framework catalogue (key, name, version).                                                                              |
  | `posture_summary`                                     | API, conversation | The board period's label, seven counts (open, above appetite, reported, approved, closed, overdue actions, reviews due), and for up to five top risks above appetite their reference, title and treatment. No owner name (#6). |
  | `control_test_steps`                                  | API, controls     | One library control's code, title, description and guidance. No organisation data.                                                                                                                                             |
  | `ai_act_classification`, `ai_act_obligation_guidance` | API, controls     | The AI system's profile fields, and for guidance the obligation's key, article and the stored class (below).                                                                                                                   |

  **No purpose sends a person's name or email from a user record**: no display name, email address or user id of a reporter, owner, reviewer, approver or administrator. Free text that people typed (a reporter's messages, risk text, an organisation's or AI system's description, a risk title) is sent as written and can mention anyone. The concern conversation asks about the location or owner of what is at risk, so a reporter may type a colleague's name.

- **Untrusted input.** Reporter text, risk text and organisation answers go only into user-role messages, wrapped by `wrapUntrusted(tag, text)`, which escapes `&`, `<` and `>` so the text cannot close or open a delimiter. System prompts hold only data every member may read: the organisation profile, site names and the control library (codes and titles; requirements by reference only, no ISO text).
- **Untrusted output.** Requests ask for a strict `json_schema` response and the gateway validates it with Zod. Invalid output is retried once, then the user gets the manual path with a plain message. Control and framework codes in the output are checked against the library server-side, and unknown ones are discarded and counted. No tool or function calling is offered to the model.
- **No official change from AI.** Model output is stored only as a suggestion, a draft or a labelled estimate (`RiskControl` with `source: "ai"` and status `suggested`, a `suggested` framework row, `Risk.aiEstimate`). Only a person's explicit action (accept, confirm, use the estimate, send the report) turns it into a record, and that action is audited as theirs.
- **Recording.** Every call is an `AiInteraction` row (purpose, model, routing, request, response, status, attempts, outcome), append-only for `isms_app` except `UPDATE` on `outcome` and `discardedCount` (a person's later decision on the suggestions and the worker's count of discarded codes); every other column is unchangeable, and DELETE and TRUNCATE are revoked. Operational logs carry event names, ids and counts only, never prompt or response content, reporter text or the key.
- **EU AI Act purposes (#16).** `ai_act_classification` and `ai_act_obligation_guidance` are synchronous API calls on the controls model, gated by `aiact.manage` and by the module being on. They send only the AI system's profile fields (name, description, intended purpose, role, supplier, model, uses a general-purpose model) inside `wrapUntrusted`, and for guidance the obligation key, its article and the stored class. No person names, emails, owner or department names, linked risk titles or notes. Drafted answers must pass the same contract schema as a save (else `aiUnavailable.invalidOutput`); the class always comes from `classifyAiSystem` on the server, and a saved AI-assisted classification records `source: "ai_assisted"` after checking the draft's `AiInteraction`.
- **AI off.** Every slice workflow works without AI: reporting by the step form, controls added from the library search, frameworks chosen by hand. With AI off, no new AI action is offered (no conversation, no "Suggest controls", no framework suggestion button); records made with AI earlier keep their AI labels as provenance.

## 10. The provider key

- **Write-only.** An administrator pastes the OpenRouter key in Settings → AI assistant. No API response, page, log, trace, audit payload or error contains it; the screen shows only that a key is set, its last 4 characters, who set it and when. It can be replaced or removed, never read back.
- **Sealed at rest.** The key is sealed with AES-256-GCM (random IV, authentication tag) under `AI_SECRETS_KEY`, which comes from the environment or secret store and never from the database. A wrong or missing `AI_SECRETS_KEY` makes the key unreadable, and AI reports itself unavailable rather than failing open.
- **Plaintext in memory.** The key is decrypted whenever it is needed and never kept. Every readiness check decrypts it to prove it is readable and discards the result (`keyReadable`, `packages/ai/src/readiness.ts:47-54`), and so does the settings GET (`apps/api/src/ai/ai-settings.view.ts:27-35`, plus one readiness check per business purpose). A call (`gateway.run`, and the connection test) decrypts it again to build the provider (`packages/ai/src/gateway.ts:61-73`), which holds it for that call only. Each opening leaves a short-lived plaintext copy on the heap until it is garbage-collected; none is written anywhere.
- **Step-up and audit.** Every settings write (`recentAuth`) needs a sign-in within the last 300 s, and only the `settings.ai.manage` permission (administrators) reaches the screen. Key set, replaced or removed, model, privacy and switch changes and connection tests are audit events with actor and time; the key itself is never recorded.

## 11. Evidence storage and transcripts

- **Uploads.** Authorisation runs before the body is read (`RawUpload.read()` is called only after the guards and the service's scope check), so a refused caller never makes the API buffer a file. The body limit is `EVIDENCE_MAX_BYTES` (413 above it). The declared type, the extension and the file content must agree on an allowed type; the check reads the whole received file (signatures for binary types, valid UTF-8 without NUL bytes throughout for text types). File names are cleaned of paths, control and bidi characters.
- **Integrity.** The API computes the SHA-256 itself and sends it to the object store as `ChecksumSHA256`, so the store refuses a body that does not match. Downloads stream through a verifier that recomputes the hash and cuts the transfer short on a mismatch (logged as `evidence.integrity_failure`); the SDK also verifies the stored checksum. The hash is shown on screen and sent as `X-Evidence-SHA256`.
- **Serving.** Downloads are always `Content-Disposition: attachment` with an RFC 5987 file name and `X-Content-Type-Options: nosniff`, never rendered inline.
- **Immutability.** `Evidence`, `EvidenceControl`, `RiskVersion`, `Approval` and `ConcernMessage` are append-only for `isms_app`, as are `AuditEvent`, `RiskScale`, `RiskScaleLevel`, `ControlTest`, `ControlTestEvidence` and `BoardNarrative`: eleven tables, each marked `/// Append-only` or `/// Insert-only` in the schema, with `UPDATE`, `DELETE` and `TRUNCATE` revoked in the migrations. `packages/database/test/append-only-grants.int.test.ts` derives the list from those annotations and checks the privileges of each (section 4). Evidence is additive; an object is deleted only when its own database transaction failed.
- **Transcripts (restricted access).** A concern's conversation transcript is read only by its reporter, an organisation administrator, or a holder of `ai.transcripts.read` at the risk's scope who may also see the risk (`mayReadTranscript`, the one rule for the route and for `can.readTranscript`). Anyone else gets 404, whether or not it exists.

## 12. Separation of duties

- **Server-side only.** Who may approve is decided by the API (`approvalRefusalFor`): the reporter never approves their own risk; the reviewer (who submitted it, holding `risks.review` at its scope) may approve a risk within appetite and not treated by Accept without holding `risks.approve` (spec §8.3); above appetite or under Accept an independent holder of `risks.approve` is required. The web shows the API's `viewerRefusal` and offers no override, and no role or setting bypasses it.
- **Row lock.** Submit, approve and return take `SELECT … FOR UPDATE` on the risk row, then check the expected version and the rule inside that transaction, so two decisions cannot race.
- **Current roles.** The rule uses the approver's role assignments from the database, never roles from the token or the session. Approve and return re-read them inside the transaction, after the row lock, with `SELECT … FOR SHARE` on the actor's `RoleAssignment` rows: a revoke committed while the decision waited for the lock is honoured, and a revoke that starts later waits for the decision to commit. (The gap noted here before the Plan 3 final review is closed.)

## 14. Modules

- **Optional modules.** The EU AI Act module (#16, spec `docs/superpowers/specs/2026-11-08-eu-ai-act-module-design.md`) is the first. The table `OrganisationModule (key, enabledAt, enabledById)` holds the modules switched on: a row present means on, absent means off. An administrator switches one with `PUT /api/v1/organisation/modules/{key}` (`organisation.manage`), audited as `organisation.module_enabled` or `organisation.module_disabled` in the same transaction; setting the state a module already has writes and audits nothing (`apps/api/src/organisation/organisation-modules.service.ts`).
- **Off means 404.** While a module is off, every one of its routes answers `404 NOT_FOUND`, whoever asks. The check is `ModuleGate` (`apps/api/src/authorization/module-gate.ts`), which `AccessGuard` runs after authentication and before the permission check (section 3). Turning a module off deletes only the `OrganisationModule` row: the module's data (`AiSystem`, `AiSystemObligation`, `AiSystemRisk`) is kept unchanged and shows again when it is turned back on.
- **Mutable tables.** `OrganisationModule`, `AiSystem`, `AiSystemObligation` and `AiSystemRisk` are deliberately mutable for `isms_app` (migration `20261111000200_ai_act`); their history is in the audit trail (section 4).
- **Permissions.** `aiact.read` (every role except `contributor`) and `aiact.manage` (`ciso`, `risk_owner`) are organisation-scoped only (section 3). Linked risks are shown only when the viewer may see them; a risk the viewer may not see is 404.
- **Audit.** Every change to the register is audited with its actor: `ai_system.created`, `ai_system.updated`, `ai_system.classified`, `ai_system.obligation_updated`, `ai_system.risk_linked` and `ai_system.risk_unlinked`. The payloads record free text by length only (`{ changed, length }`), an obligation's note only as `noteChanged`, and a risk link by the risk's id and R-reference, never its title.
- **AI assistance.** The two AI Act purposes send the AI system's profile fields only, never person names, emails, owner or department names, linked risk titles or notes (section 9). They are gated by `aiact.manage` and the module being on, the output is a draft a person reviews, and the class is always decided by the rules on the server. Everything works with AI off.
- The module's own security notes are in `docs/security/eu-ai-act.md`.
